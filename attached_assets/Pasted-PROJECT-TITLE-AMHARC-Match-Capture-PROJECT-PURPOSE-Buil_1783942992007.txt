PROJECT TITLE
AMHARC Match Capture

PROJECT PURPOSE
Build a production-oriented prototype of AMHARC Match Capture.

AMHARC Match Capture is a hybrid, local-first sports video capture, recording, live-production, PTZ control, event-tagging and streaming platform designed for:

- Gaelic football
- Hurling
- Ladies’ football
- Camogie

The platform must capture live video from professional IP cameras, record full matches locally, support manual pan-tilt-zoom control, accept event-tagging input from a 15-button Elgato Stream Deck, generate broadcast-style overlays, stream matches live and export structured match data for later AMHARC analysis.

This is not a conventional web application and must not be implemented as a browser-only video uploader.

The system must use a hybrid architecture comprising:

1. A local Windows Capture Agent running on the match laptop.
2. A browser-based Operator Interface.
3. A local SQLite database.
4. A local WebSocket and HTTP API between the Operator Interface and Capture Agent.
5. A modular camera-adapter architecture.
6. A media-processing pipeline based on FFmpeg or GStreamer.
7. Optional cloud services for remote administration, account management or off-site metadata synchronisation.

The local Capture Agent must remain fully operational without Internet access.

REFERENCE HARDWARE

The initial reference hardware is:

- AXIS Q6128-E 50 Hz outdoor PTZ network camera
- PoE+ power source
- Ethernet connection between camera and laptop
- Windows 11 laptop
- Local NVMe SSD
- Axis joystick or compatible USB joystick
- Elgato Stream Deck with 15 buttons
- Optional USB microphone or commentary audio interface
- Optional Internet connection for live streaming

The AXIS Q6128-E must be treated only as the first reference implementation.

The architecture must not make Axis a permanent dependency.

The system must later be capable of supporting other cameras through adapters, including:

- Canon
- Panasonic
- Sony
- Axis
- PTZOptics
- BirdDog
- AVer
- Bolin
- ONVIF-compatible cameras
- Generic RTSP cameras

CORE ARCHITECTURAL PRINCIPLES

The implementation must adhere to the following principles.

1. Local-first operation

Recording, event tagging, PTZ control, match timing and local metadata capture must continue when Internet connectivity is unavailable.

2. Camera neutrality

Camera-specific behaviour must be isolated behind interfaces and adapters.

3. Open protocols

Use established protocols and manufacturer-supported interfaces where possible, including:

- RTSP
- RTP
- ONVIF
- VAPIX
- RTMP
- SRT
- NDI or NDI HX where appropriate
- HTTP
- WebSocket

4. Resilient recording

A camera disconnect, application failure or loss of Internet access must not invalidate an entire recording.

5. Clean separation of services

The following must remain separate modules:

- Camera connection
- Video preview
- Video recording
- PTZ control
- Joystick input
- Stream Deck input
- Match clock
- Event tagging
- Broadcast overlays
- Live streaming
- Storage monitoring
- Metadata export
- Health monitoring
- Logging

6. Single authoritative match timeline

Video, match clock, recording time, event tags, score, periods and broadcast overlays must share a synchronised time model.

7. No vendor lock-in

All metadata and event data must be exportable in open formats.

8. Safe failure behaviour

Local recording must continue even if:

- the live stream fails;
- the overlay engine fails;
- the Internet connection fails;
- the cloud service becomes unavailable.

9. Structured documentation

The repository must contain formal documentation for requirements, architecture, interfaces, APIs, testing and deployment.

10. Incremental delivery

Do not attempt to build the entire system in one step.

First produce the design, contracts and backlog.

Then implement the system in phases.

SYSTEM CONTEXT

The application will normally operate as follows:

- The camera is mounted on a telescopic mast.
- The camera receives power through PoE+.
- The camera connects to the Windows laptop by Ethernet.
- The operator views the live camera feed on the laptop.
- The operator controls camera pan, tilt and zoom using a joystick.
- The operator presses Stream Deck buttons to tag important events.
- The system records the full match locally.
- The system maintains a match clock and scoreboard.
- The system can generate a clean video feed.
- The system can generate a programme feed with broadcast overlays.
- The system can live stream the programme feed.
- The system stores match metadata and events for later AMHARC analysis.
- The system must work at grounds where no reliable Internet connection exists.

NON-FUNCTIONAL REQUIREMENTS

RELIABILITY

- Full-match recording must operate for at least two hours.
- Recording must survive Internet loss.
- Prior segments must remain usable after application failure.
- Camera reconnection must be attempted automatically.
- Stream failure must not stop recording.
- Overlay failure must not stop clean recording.
- Events must be stored immediately.
- Score changes must be auditable.
- The application must support recovery after abnormal shutdown.

PERFORMANCE

- Support one 4K camera stream.
- Support 1080p50 for the initial AXIS Q6128-E implementation.
- Support future multi-camera operation.
- Avoid unnecessary transcoding.
- PTZ controls must feel responsive.
- Stream Deck events should be timestamped within 100 milliseconds where practical.
- Operator interface updates should appear in near real time.
- Preview latency must be sufficiently low for joystick PTZ operation.

USABILITY

- One trained operator must be able to run the system.
- Match setup should normally take less than five minutes.
- Recording state must be visually unmistakable.
- Critical warnings must use text and icons, not colour alone.
- The interface must be usable in outdoor lighting.
- The interface must support full-screen mode.
- Common actions must be available without opening menus.
- Destructive actions must require confirmation.
- Undo must be available for common tagging and score actions.

ACCESSIBILITY

- Support keyboard navigation
- Provide visible focus states
- Use sufficient contrast
- Avoid colour-only meaning
- Support scalable text
- Provide accessible labels
- Provide operator notifications in text form
